1The 30-second story

Dorothy is 74. Her Whirlpool dryer runs, but the clothes come out cold. A tech visit costs about $200. The fix is a $9 thermal fuse and 15 minutes. She has a flip phone, and she never touches a screen.

1
☎️She calls one number

Fixie says it's an AI and that the call is recorded. It gets her model number by voice and reads it back once. It names the part (WP3392519) and warns her the vent is clogged, which is a fire risk.

2
📞📞📞📞Four calls at once

After she hangs up, Fixie calls the warranty line and three parts counters in parallel. A tool call puts each quote on the board during the call.

3
🛑Code says no

Valley quotes $55 + $4. That's $59 landed, over her $40 cap, so it's rejected. Coast doesn't pick up, so it's skipped with no retry. The code decides both, not the model.

4
🔁Callback

Fixie calls back the number she called from: "You called at 7:46… $13.05, arrives Tuesday. Want me to order it?" Nothing happens until she says "order it."

5
📦Delivery day

A carrier webhook (simulated tonight) says the box arrived, and Fixie calls her again. The code won't let it reach "plug it back in" until she confirms the dryer is unplugged and the vent is cleared.

6
🔥"It's warm!"

Fixie records the fix as verified. That verified outcome is the data behind the long-term "fixed, or we pay the pro" story.

The job's life, as a state machine (types.ts → JobState)

NEW→DIAGNOSED→SOURCING→AWAITING_CONFIRMATION→ORDERED→DELIVERED→INSTALLING→FIXED
Side exits: DECLINEDshe says no ESCALATEDsafety keyword, unknown model, no usable quote, 2 failed callbacks STOPPEDkill switch or agent-spend cap NOTIFIEDenterprise end state (port fault)

Every arrow is one call to jobs.transition(id, from, to), a synchronous compare-and-set. If the job isn't in from, the call returns false and changes nothing. That's why a trigger can fire twice safely.

2What actually happens on a call

Read top to bottom. The model talks; our server decides. Every arrow into the orchestrator goes through /vapi/webhook, which turns raw Vapi JSON into a small typed CallEvent. In sim mode, vapi/sim.ts POSTs the same Vapi-shaped JSON to the same webhook, so sim runs the real pipeline.

voice (audio on the phone line) HTTP / webhook / API reply

3The pieces

About 2,500 lines of TypeScript on Node 22 and Express, run with tsx. Each module has one job. The arrows only go one way: Vapi → webhook → orchestrator → dialer → provider.

The edge: talking to Vapi

vapi/webhook.ts

The front door. Vapi POSTs every event here: tool calls, status updates, transcripts, and end-of-call reports. It checks the shared secret, works out which call the event is for, turns the JSON into a CallEvent, and hands it to the orchestrator. It always answers HTTP 200, and it answers tool calls in under 900 ms.

Vapi's JSON is messy: arguments can be an object or a string, there are two tool lists, and fields go missing. All of that mess stays in this one file. If a tool reply is slow, the phone goes silent.

vapi/assistants.ts

Builds the assistant JSON for each call: model, tools, server URL plus secret (on the assistant and on every tool), max duration, and silence timeout. It deliberately leaves out voicemail detection.

Each outbound call gets a fresh transient assistant with this job's facts baked in, so the supplier call already knows the part number.

vapi/prompts.ts

The system prompt and first message for each lane: intake, warranty, supplier, callback, delivery, and tech. They're written to be spoken, and every first message says "AI assistant… this call is recorded." Part numbers are spelled out in chunks ("W P 3, 3 9 2, 5 1 9").

FCC 24-17 treats an AI voice as "artificial", and California PC 632 requires consent to record. The disclosure comes first on every call.

vapi/client.ts

Live provider. Places calls with POST /call and ends them through the call's controlUrl. On a 5xx it retries once after 2 s. On a 4xx it throws, and the dialer retries once after 5 s only if the error is a concurrency limit.

Implements VoiceProvider, so the dialer never knows whether a call is real.

vapi/sim.ts

Sim provider. It pretends to be Vapi: it generates the exact webhook JSON a real call would produce and POSTs it to our own /vapi/webhook. Each roster entry has a persona (quote:9.10:3.95…, no_answer, out_of_warranty). It reads our tool replies back as the agent's next line.

It's the dev harness, the regression test (npm run demo:sim), and the stage fallback, and it covers 100% of the server path.

boot.ts + scripts/

ensureInbound() PATCHes the intake assistant's server URL to PUBLIC_URL on every boot. setup-vapi creates the assistant and attaches the number. preflight prints a ✅/❌ go/no-go table.

The tunnel URL drifting is the classic way to kill a live demo.

The brain: decisions

orchestrator.ts

The lifecycle, about 740 lines. It handles each tool (start_job, record_quote, record_order_decision, safety_ack, install_progress, report_fix), decides when sourcing starts and when the callback fires, ranks quotes, manages timers, and runs the kill switch and the port-fault flow.

It's the one place that knows the business process. It never sees raw Vapi JSON, and it never trusts a phone number or a price from the model.

guards.ts

Every guardrail as plain functions: reserve, settle, checkQuote, checkStuck, checkSpend, canAdvanceInstall, safetyKeywords. Each one returns a verdict with a deterministic, human-readable reason. They're unit-tested.

"Enforced in code, not the prompt" is the Unsupervised-track claim. This file is the proof.

dialer.ts

The only place a call is placed. It looks up the destination (a roster entry, or the job's own caller ID), runs guards.reserve() before the first await, picks live or sim per lane, and registers the call. It emits call_started with a masked phone number.

One chokepoint means one place to audit. The LLM can't put a phone number in front of it.

parts.ts

The seeded catalog. It fuzzy-matches the model (edit distance ≤ 2, so "WED4851EW" still finds it), maps the symptom to a fault, and checks isIdentical(partNumberSaid) against the part number plus its cross-refs, with or without the "WP" prefix.

"Same part?" is answered by code comparing strings, not by the model guessing.

The memory: state and contracts

contracts.ts

The frozen interfaces: CallEvent, CallCtx, VoiceProvider, Guards, Jobs, Dialer, and Orchestrator. Frozen at 2:50 PM.

Four build agents coded against these at the same time without stepping on each other.

types.ts

Domain types: Job, Quote (with landedTotal and rejectedReason), GuardVerdict, and FixieEvent (with simulated).

identicalPart is documented as "computed in code, never trusted from the LLM."

jobs.ts · calls.ts

The job store, with CAS transitions and an atomic snapshot to data/jobs.json (write a temp file, then rename). Also the call registry: which callId belongs to which job, lane, vendor, and epoch.

The demo survives a server restart, and racing triggers can't double-fire.

events.ts

The event bus. Every emit() gets a monotonic id, is appended to events.jsonl, and is pushed over SSE /events, with replay from Last-Event-ID. maskPhone() turns numbers into ···0142.

One stream drives the board, the replay, and the audit log.

config.ts

Every cap and timer comes from env vars with demo defaults. It also holds the per-lane live|sim mode (switchable at runtime with POST /demo/mode), the demo epoch, and the admin token.

Per-lane mode is what makes the fallback ladder possible.

routes.ts

Admin routes behind the x-admin header: /simulate/delivered, /fault, /jobs/:id/stop, /demo/reset, /demo/mode, /demo/sim-intake. Public routes: /jobs with masked phones.

The server sits on a public tunnel, so a stranger mustn't be able to fire the port fault or stop a job.

The surfaces (judges and family, never Dorothy)

web/ (judge board)

The "OPERATOR AUDIT VIEW": call lanes with live transcripts, a quote table with rejected rows struck through, the guard ticker, meters, two savings counters, and a SIMULATED badge. Hidden hotkeys: D (delivery), P (port fault), X (kill switch).

Judges can't hear four phone calls at once, so the board makes the invisible work visible.

site/ (website + dashboard)

A Next.js site with sign-in and a /dashboard where a caregiver or operator can see jobs and stop one.

Family members want to watch over the job. Dorothy still never needs it.

vision/ (in progress)

"Can I take a look?": an optional photo of the nameplate, receipt, or part label, processed in three tiers. Images stay in memory only, with a 1-hour TTL.

Reading a model number aloud is the weakest link in voice. See §7.

5Sim vs live

Be precise about this before a judge asks. Every simulated event carries simulated: true, and the board shows an amber SIMULATED badge.

Real tonight

  • Dorothy's call over the real phone network: phone → Twilio number → Vapi intake assistant (Claude).
  • Real outbound calls to real phones held by teammates and friends, placed in parallel.
  • Quote capture through in-call tool calls, the part-number check, landed-total ranking, and every guard.
  • The callback to the caller-ID number, and the "order it" decision.
  • The delivery call and the install gate.
  • The event stream, the board, the kill switch, and the spend meter.

Simulated or mocked, and said out loud

  • The suppliers are friends. Their prices are role-play numbers taken from real listings.
  • The order is mocked. No money moves. order_confirmed carries mockOrder: true.
  • The delivery webhook is fired by a hotkey and shaped like a carrier webhook (simulatedWebhook: true).
  • The port fault is sim-only and labeled "simulated Samsara webhook."
  • The catalog is seeded; there's no learned parts graph. The diagnosis confidence (0.82) is labeled "lookup prior."

Why this is honest, not a fake demo

The sim doesn't skip anything. It POSTs the same Vapi-shaped JSON into the same /vapi/webhook, so the orchestrator, guards, ranking, and CAS states can't tell the difference. When a lane is in sim, only the voices are fake; the decisions are the same code. We say "friends are playing the counters" in the first 10 seconds, before anyone asks.

L0All live.
L1One call doesn't ring within 10 s: flip that lane to sim.
L2Two calls fail: suppliers to sim. Dorothy's calls stay live.
L3Tunnel or intake dead: all sim, with the badge.
L4Backup video, plus a replay of a recorded events.jsonl.

6The tech choices, and why

Vapi

Voice orchestration, not ours to build

Vapi runs the hard real-time loop: phone audio → speech-to-text → LLM → text-to-speech, with barge-in and turn-taking. It calls our server for each tool call. Transient assistants let each outbound call carry its own prompt (this part number, this customer, this price). Building that audio pipeline ourselves would have eaten the whole hackathon.

Twilio

A real phone number

We use a paid Twilio number imported into Vapi, because free Vapi numbers can't place outbound calls. A real phone-network number is the whole No App story: Dorothy can use a landline or a flip phone, with nothing to install and no account to make.

Claude, two tiers

Sonnet for Dorothy, Haiku for the counters

Sonnet runs the intake, callback, and delivery calls, which are long, open-ended, need empathy, and have to follow a multi-step install. Haiku 5.5 runs the warranty, supplier, and tech calls, which are short and scripted, run many at once, and where speed and cost matter most. Either way, the model's only job is to talk and call tools. It doesn't make the decisions.

cloudflared

A public URL for the webhooks

Vapi has to reach our laptop over HTTPS. We run one long-lived quick tunnel, so restarting the server doesn't change the URL. On boot, ensureInbound() PATCHes the intake assistant to the current PUBLIC_URL, and preflight checks that they match. We run npm start, never dev, because file-watch restarts would wipe state mid-demo.

Frozen contracts

How four build agents worked in parallel

At 2:50 PM, contracts.ts froze the seams between modules. Each workstream got its own files and coded against interfaces it couldn't change: WS-1 engine core (guards, parts, jobs, calls), WS-2 orchestrator (dialer, lifecycle, routes), WS-3 Vapi live (client, assistants, prompts, webhook), and WS-4 simulator. The key choice was VoiceProvider: live and sim implement the same two methods, so the simulator could be built and tested without anyone having Vapi keys. And because CallRequest deliberately has no to field, the type system makes "the orchestrator picks a phone number" impossible.

interface VoiceProvider { createCall(req): Promise<{callId}>; endCall(call): Promise<void> }
interface CallRequest  { lane: Lane; vendorId?: string; maxSec: number }   // no `to`: the dialer resolves it
type CallEvent = {kind:'tool'…} | {kind:'status'…} | {kind:'transcript'…} | {kind:'ended'…}
Synchronous guard reservation

Why reserve() runs before the first await

Node runs one piece of JavaScript at a time and only switches tasks at an await. If the check were async ("look up the count, then dial, then increment"), four parallel dials could each read "7 of 8 used," all pass, and place 11 calls. That's the classic check-then-act race. Instead, reserve() checks and increments the counters in one synchronous step, so each dial sees the previous one's reservation. When a call ends, settle() corrects the minutes to what was actually used.

// ❌ racy
const ok = await canPlaceCall(job)   // 4 dials all read 7/8
if (ok) { await vapi.createCall(); job.calls++ }
// ✅ dialer.ts
const v = guards.reserve(job, req)   // sync: check + increment
if (!v.ok) return emitGuard(v)
await provider.createCall(...)       // first await comes after
CAS state transitions

One winner, every race

Lots of things can trigger the same step. Sourcing starts on whichever comes first: the intake call's status: ended, its end-of-call report, or a 25 s fallback timer after start_job. The callback fires on whichever comes first: all sourcing calls ended, the warranty plus 2 suppliers ended with a usable quote, or a 75 s timeout. Each path calls jobs.transition(id, 'SOURCING', 'AWAITING_CONFIRMATION'). The first one flips the state and gets true. Everyone else gets false and does nothing. So Dorothy can never get two callbacks. The same idea is behind tool-call dedupe by toolCallId and dropping webhooks from an older demo epoch after /demo/reset.

7What's next

#11

Bayesian multimeter diagnosis

Today's diagnosis is a catalog lookup. Next, Fixie forms hypotheses and visibly changes its mind. A hand-written fault tree for "electric dryer, no heat" gives priors. Each safe test (breaker check, then fuse continuity while unplugged) updates the posterior with Bayes' rule. The next test is the one with the most information gain per unit of safety cost. start_job fires once the top hypothesis is ≥ 0.85. An ambiguous reading counts as "unknown," and two unknowns escalate to a pro. The groundwork is already in the code: record_test is in ToolName and Job.diagnosis exists.

Say on stage: "The likelihoods are expert-written, not learned. Every confirmed fix tunes them."

#12

The proof panel: "agent proposes, code approves"

  • Every decision event carries approvedBy: "code" | "user_voice" | "caregiver" and a deterministic reason.
  • An always-visible strip shows calls N/8, minutes, $ committed vs the cap, and guards fired.
  • A scrolling decision log shows the agent's proposal, then ✅ or ⛔, with the rule that decided.
  • A staged runaway: a "Hold Forever" supplier trips the stuck guard, then STOP is pressed live.
  • A judge-callable number on the last slide, with a per-caller cap (≤ 1 job, ≤ 3 calls, roster-only).

Why: judges have seen 50 "Vapi + Twilio + prompt" demos. The 2026 agent-commerce winners (AgentPay, NextWave) made the approval layer the headline.

vision/

Visual inspection: "Can I take a look?"

This is optional and never required, because of the No App rule. Fixie reads out a 4-digit code or texts a link. A family member, or Dorothy by MMS, points a camera at the nameplate, receipt, or part label.

Tier 1 · in the browserScores sharpness, glare, text, and stability, and auto-captures the best frame. Costs nothing.
Tier 2 · cheap classifierRanks the images by kind (nameplate, receipt, part label, appliance) on a thumbnail.
Tier 3 · Claude visionReads the model, purchase date, or part number from the best image plus a zoomed crop.

It stops early once each goal (model, purchase date) is confident. Images live in memory only, up to 16 per session, and are dropped after 1 hour or on reset. Why: a misheard model number is the weakest link in a voice-only flow.

site/

Website and caregiver portal

  • A Next.js site with sign-in and a /dashboard of jobs: state, transcripts, and the quote table.
  • A stop button that works: a caregiver or operator can stop any job, which ends every live call.
  • Caregiver co-sign over $50 (#13): the order is held until the daughter texts back YES (guard{cosign, held}).
  • A caregiver closing call (#8): "Your mom's dryer is fixed. $13 instead of $200."

The portal is for the family. Dorothy's interface is still just the phone.

enterprise

Same engine: ports, fleets, defense facilities

⚓ Ports

Terminal tractor YT-07 at the Port of San Diego throws J1939 SPN 3226 FMI 4, a NOx sensor fault. POST /fault runs the decode, then pro_required ("certified tech only"), sourcing against a $1,500 cap, and a call to the yard tech that ends in NOTIFIED. Crane downtime is an estimated $5k–50k+ per hour (vendor figure). Sim-only tonight.

🚚 Fleets

A telematics fault (Samsara-style DeviceHasVehicleFault) triggers sourcing before the truck is back in the yard. Samsara and Konecranes stop at dashboards and work orders. Nobody phones the parts counter.

🪖 Defense facilities

The Army created an HVAC repair task force on Oct 15, 2026. Base HVAC uses off-the-shelf parts, so ITAR doesn't apply. Vapi and Twilio aren't FedRAMP-authorized, so pitch installation facilities only, not weapons systems.

Line: "Dorothy needs no screen. The tech needs no hands. Same engine."

8Likely judge questions

Each answer takes about 15 seconds. Concede what's true, then pivot to the closed loop and the code-enforced guardrails. Click to open.

"Google's AI already calls businesses."

It does, and we never say otherwise. Google calls local services from Search and texts or emails you a summary. Fixie starts from any phone, not Search. It calls distributors by part number, gates safety, closes on a spoken yes, and calls back on delivery day to coach the install and confirm the fix. Google gathers quotes; we finish the job.

Never say: "Google can't call businesses."

"Isn't this just OpenClaw with a phone skill?"

Yes, OpenClaw can place these calls. Calling is plumbing, and we'd use it as a commodity layer. What a personal agent won't do is take a call from a 74-year-old with a flip phone, refuse the gas repair, enforce spend limits it can't override, and call back to check the fix worked. That check is the outcome data that lets us guarantee repairs.

Never say: "OpenClaw can't."

"What about liability? A 74-year-old doing electrical work?"

We only coach unplug-and-swap repairs. The safety level comes from the catalog, not the model. Gas, smoke, sparks, or high voltage go to a pro or to 911, enforced in code. The install can't reach "plug it back in" until she's confirmed it's unplugged and the vent is cleared. Every call is recorded. Long term, it's a capped "fixed, or we pay the pro" guarantee through a licensed carrier. Tonight that pricing is simulated.

"Who pays?"

Mostly not Dorothy. The buyer is whoever pays for the repair. Home-warranty companies and insurers pay per resolved case, and a $13 part beats a $200 truck roll on their books. Then fleets, ports, and base facilities, all on the same engine. An affiliate cut on parts covers the consumer line.

"Seniors get scammed by phone. Isn't this a scam vector?"

We designed for it. Adults 60+ lost $3B to fraud in 2025. Fixie only calls back the number that called in: caller ID, never a number the model heard. It opens with "the AI assistant you called at 7:46 about your dryer." It never asks for a card number, payment, or address by voice. And every call starts with "I'm an AI, this call is recorded."

"Will real suppliers even talk to a bot?"

Some won't, and that's built in. A refusal or no-answer is a guard: skipped, no retry, and the other counters still quote. That's Coast on stage. The call discloses up front, asks about one part number, and takes about 20 seconds. Workd already sells voice parts lookup to HVAC distributors. (If Lane B called a real San Diego counter today, cite that result first.)

"The No App track says no screens. Isn't the board a screen?"

The board is the operator audit view, for you, the judges. Dorothy never sees it. Her whole interface is: dial, talk, hang up, pick up. The delivery trigger is a hidden hotkey, not a button she presses. The photo by text and the caregiver portal are optional extras for family, never required.

"Were the suppliers staged?"

Yes. Friends played the counters, so we don't cold-call real businesses at a hackathon, and the prices come from real listings. The calls, the quote extraction, the part-number check, the ranking, and the guards are all live code. We say so in the first 10 seconds.

"Why trust an AI to spend money?"

We don't trust the AI; we trust the code around it. The model can't choose a phone number (the dialer has no to input), can't set the price (the order uses the server's ranked quote, never the tool's arguments), and can't exceed the caps. Nothing is ordered without the words "order it." Tonight the checkout is mocked. (Press X to show the kill switch.)

"Voice agents are a commodity. What's the moat?"

The voice agent is the commodity. The moat is the loop's data: model → part → cross-refs → price and stock per counter, plus verified-fix outcomes from the delivery callback. A personal agent never collects that, and we can underwrite a guarantee against it. It's seeded today, and we say so.

"What if the server crashes mid-call?"

The line runs as a systemd service with a watchdog. It checks the server's health and the public tunnel every 10 seconds, and restarts whichever one died. Job state survives a restart: every state change is snapshotted to disk and reloaded on boot. On boot, the server also re-points the Vapi assistant at the current tunnel URL. We never restart in the middle of a call: deploys wait until Vapi reports no active calls. Recovering webhooks that arrive while it's down is what we're building next.

"What if the diagnosis is wrong?"

A $13 part is the cheapest wrong guess in the house. The delivery call verifies the fix by voice ("Is it warm?"). If it isn't, the job escalates to an install-only pro. Next is #11: live multimeter tests that move the probability before we buy anything.
